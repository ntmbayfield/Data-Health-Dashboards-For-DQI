README

Overview of the workbook, why the inventory comes first, what each tab holds, and how they fit together.

Integration Register — Data Quality & Integrations
External sources -> Omatic Cloud (middleware) -> Salesforce
What this workbook isThe working inventory of every integration writing into Salesforce, and the governance record that sits around it. It is the weeks 1-2 deliverable of the data health dashboard project: the thing you build first, by interviewing the five units, before any dashboard is designed or any code is written.
Why the inventory comes firstNobody can govern a set of pipelines they cannot list. In most decentralised operations no single document names every integration, its owner, its cadence and when its mapping was last reviewed - which means risk is invisible rather than accepted. Building that list is roughly 80% of the total value of this project and requires no engineering at all. Seven risk findings on the Risk Findings tab were produced from the inventory alone, before a single record was examined. Expect to discover integrations nobody centrally knew existed; those discoveries usually justify the effort on their own.
What it feedsEvery field on the Integration Register becomes a field on Integration_Definition__c in Salesforce, and every dashboard in the mockup deck is a view over it. Board 01 is this register rendered. Board 02 rolls the run log up by the units named here. Board 06 filters everything to one unit using the Unit x Integration Map. Nothing downstream is buildable until these tabs are populated and signed off.
How to use itWork one unit at a time using the Unit Interview Guide. Fill the YELLOW cells. GREY cells are formulas - do not type over them. PINK marks something that needs escalation rather than documentation. BLUE marks an integration shared between two units. The nine rows already present are the known inventory as stated; add rows as you find more.
Scope of this versionNine integrations, five units, seven source systems. Gratavid and Greater Giving are single vendor accounts serving two units each and are recorded once with a primary and a secondary owner. This is a five-unit proof of concept; the same structure scales to thirty units by adding rows, not columns.
The tabs
#TabWhat it holdsWhy it exists
1Integration RegisterOne row per integration: owners, source and target, method, cadence, mapping version, the two attestation dates, risk tier, sensitive data, status.The spine. Everything else in the workbook and every board in the deck is derived from or joins back to this tab.
2Unit x Integration MapWhich units see which integration, who is primary, who countersigns a mapping change.A shared vendor account serves two units, so unit membership is many-to-many and cannot live in a single column on the register. This tab is what makes the per-unit dashboards possible.
3Build RequirementsAll twelve build requirements with acceptance criteria, owners and the reason each cannot wait.Separates what must be built from what must be decided. A requirement has an acceptance test; a decision has a person. Conflating them is how governance work stalls.
4Implementation DecisionsFifteen decisions, each either open or governed by a build requirement.The open items are the agenda for the definitions review. The governed items record which requirement settled the question, so the reasoning survives the people who were in the room.
5Detection MethodsThe logic behind every alert: the rule, what it catches, what would go undetected without it, and the false-positive risk.The tab to read before challenging a number. Several alerts - the create:update canary especially - fire on runs that reported success with zero errors, and look like false alarms until the method is understood.
6Unit Score ModelThe four components of the unit data quality score, their weights, formulas, normalisation and known distortions.A composite score compresses four unrelated things into one number. This tab is where the compression is documented and where the warning about publishing letter grades lives.
7Cadence & Stale ConfigExpected cadence, grace, last successful run and expected next run for each integration.Staleness has to be derived from an expectation because a stopped integration writes no log rows. Four of nine integrations are bursty and need a manually set next-run date instead of a cadence.
8Field Write MatrixWhich integration writes which Salesforce field, with a writer count per field.Multi-writer conflicts are invisible at runtime - every write succeeds and the last one wins. This is the only place they can be seen, and it is derived from configuration rather than data.
9Risk FindingsEight findings with severity, status, why each is a problem and the recommended control.What the inventory revealed. Two are already closed or addressed by build requirements; the rest are live.
How the tabs fit together
StagePath through the workbookWhat happens here
1. InventoryUnit Interview Guide -> Integration Register + Unit x Integration MapYou cannot govern what you cannot list. Interviews populate the register; the map records shared ownership.
2. AnalysisIntegration Register -> Field Write Matrix + Cadence & Stale Config -> Risk FindingsTwo derived views of the register expose problems no one had to look at data to find: fields with more than one writer, and integrations whose silence would go unnoticed.
3. ResponseRisk Findings -> Build Requirements + Implementation DecisionsEvery finding resolves into something to build or something to decide. A finding with neither is just an observation and will not survive the quarter.
4. InstrumentationBuild Requirements -> Detection MethodsThe requirements make the signals capturable; the methods define what each signal means and what it catches. BR-8 exists so the canary in Detection Methods is computable at all.
5. MeasurementDetection Methods -> Unit Score Model -> the six dashboardsAlerts roll up into the four score components. The score is the last thing built, not the first, because it is meaningless until everything above it is in place.
Companion artifactThe dashboard mockup deck - six boards plus a margin reference key - is the design that these tabs produce. Read the register first; the boards make considerably more sense once you know what is on them.

Build Requirements

All twelve requirements with acceptance criteria and the reason each cannot wait. A requirement has an acceptance test.

IDRequirementStatusApplies toWhat gets builtAcceptance criteriaOwnerDueWhy it cannot wait
BR-1Provenance on every record from day oneProposedAll integrationsSource_System__c (picklist), Created_By_Run__c and Last_Integration_Update__c (Lookups to Integration_Run__c), and Source_Record_Id__c as a unique External ID, on Contact, Account and Opportunity. Plus a dedicated Salesforce integration user per pipeline, so CreatedById is provenance for free on every object.100% of records created by an integration user in the trailing 7 days carry a non-null Source_System__c and Created_By_Run__c. Rule C10 reports the residue and must trend to zero.Cannot be applied retroactively. Without it every defect is orphaned - you can count problems forever and never attribute them to a unit or a pipeline. Three things on the boards exist only because of it: human-account write detection, defect attribution, and the unit scores.
BR-2Mandatory intake for manual uploadsProposedAny load not run by an integration userPreferred path: manual files routed through an Omatic file-import profile so the run is logged structurally. Exception path: a Screen Flow capturing submitter, unit, purpose, target objects, source file and row count, which creates the Integration_Run__c and returns its ID. Data Loader access restricted to trained users.Zero Contact or Opportunity records created in a 30-day window by a named human account with no associated Integration_Run__c. Any that appear are reported as an exception with the person named.A manual CSV leaves no trace. Without this the seven-day log is systematically biased toward the well-behaved pipelines and excludes the activity most likely to cause damage - ad hoc, unmapped, unreviewed, unowned.
BR-3Expected next run date set as the closing step of every bursty runProposedGreater Giving, SIS, Gravyty, iWaveExpected_Next_Run__c on Integration_Definition__c. Staleness for these four derives from that date rather than cadence. The run cannot be marked complete until the field is set - enforce with a validation rule on Integration_Run__c.Status = Complete.All four low-frequency integrations carry a future Expected_Next_Run__c at all times. The board shows 'NO NEXT DATE SET' rather than silently passing when blank.Four of nine integrations run in bursts. Cadence-based staleness would show 44% of the register permanently red, which teaches people that red means nothing and destroys the most valuable panel in the suite. Close of run is the only moment anyone knows the answer.
BR-4Three-bucket outcome modelProposedEvery run, every dashboardRecords_Rejected__c (did not load), Records_Loaded_With_Warning__c (loaded carrying a known S1 defect), Records_Loaded_Clean__c. The warning bucket is populated by evaluating the S1 rule set at load time, not overnight, so the defect is written with Introduced_By_Run__c already populated.Rejected + warned + clean + unchanged + skipped = rows in file, on every run, with no residual. All three columns shown; no single 'success' figure reported anywhere.Two buckets produce a log reporting 99.6% success while the defect backlog grows. The warning bucket is the join between the pipeline dashboards and the data health dashboard - without it those two halves contradict each other in public, and defect attribution does not work at all.
BR-5Student ID crosswalk on the graduate importProposedGraduate import (INT-006)SIS student ID stored on Contact as a unique External ID at first load, with Omatic configured to key on it before any name or date-of-birth fallback. The December cycle runs as an upsert, not a fresh match.Currently zero of 3,959 loaded graduates carry one, which is 2,168 open defects from a single run. Blocking for December: retrofitting after another name-and-DOB load costs more than building it now, and 44% of each incoming cohort already exists in Salesforce, so weak matching makes this the largest single source of duplicates.
BR-6Attestation as a record, not a checkboxProposedAll integrationsTwo independent dates - Mapping_Last_Modified__c from Omatic and Mapping_Last_Attested__c from a human - plus the version reviewed, the reviewer, the method used (visual check / sample record trace / sandbox round-trip) and any accepted exceptions. Attestation history retained.Every integration carries both dates or an explicit 'never attested'. The register flags any row where modified is later than attested.Tracking only 'last modified' inverts the signal: a mapping changed last week reads as current when it is unreviewed. Three of nine integrations are currently in that state, including the one that loaded 4,102 graduates two days after being modified. A checkbox gets clicked reflexively; a form asking for version and method does not.
BR-7Source and target schema fingerprintingProposedAll integrationsOn every run, capture the field list the source returned and diff against Source_Schema_Fingerprint__c. Separately, for each mapped Salesforce field capture API name, type, required flag and active picklist values, and diff against last known good.Drift raised within one run of a source or target change, with the changed fields named. Acknowledge-and-refingerprint clears it.Neither kind of drift throws an error. A source adding a field means the integration runs green while dropping data; a unit admin tightening a validation rule or picklist breaks it from the target end, which is the more common outage in a Salesforce org. A semiannual review finds these up to six months late.
BR-8Rolling create:update baseline per integrationProposedAll integrations that create ContactsStore Contacts_Created__c and Contacts_Updated__c as separate counters on every run and maintain a trailing six-run mean of the ratio per integration, with a per-integration variance threshold (default 100%).Every run has a computed ratio and a variance figure against its own history. Alerts suppressible per run with a reason, never per integration.This is the only detection for matching logic failing silently. The run completes, status is success, error count is zero and correctly so. Roll created and updated into a single 'records processed' figure to save a column and the alarm becomes unbuildable - there is nothing left to compare.

Suppression volume reported alongside backlog.Some defects genuinely cannot or should not be fixed. Detection Methods

The logic behind every alert — what it catches and what would go undetected without it. Read this before challenging a number.

#AlertLogicWhat it catchesWhat it would look like without this checkFires onFalse positive risk
1Unattested change in productionFlag when Mapping_Last_Modified__c > Mapping_Last_Attested__c. Two independent dates: modified comes from Omatic, attested is entered by a human who compared the live mapping to the documented spec and signed the version number and the review method.A mapping that was reviewed, then changed afterwards, and is now running unreviewed. Three of nine integrations are in this state — including the SIS pipeline, which was attested on 9 May, modified on 11 May, and loaded 4,102 graduates on 26 May. The mapping that ran was not the mapping that was reviewed.Tracking only 'last modified' inverts the signal. A mapping changed last week reads as fresh and current when it is actually unreviewed; a mapping untouched for three years reads as stale when it may be perfectly correct. Neither state is distinguishable from the other with one date, so the whole check silently does nothing.NightlyLow. A reviewer who attests without checking defeats it, which is why the attestation form captures the method used, not just a checkbox.
2Source schema driftOn every run, capture the field list the source returned and diff against Source_Schema_Fingerprint__c from the last successful run. Any addition, removal or rename raises drift.A source system quietly adding or renaming a field. Greater Giving added a 'Platinum Plus' sponsorship tier; the integration kept running and dropped it.No error is thrown. The integration runs green while losing data, and the loss is only found when someone looks for a record that should exist. A semiannual mapping review would find it up to six months later.Every runLow, but noisy if the source adds fields often. Acknowledge-and-fingerprint resets it.
3Target schema driftSame diff on the Salesforce side: for each mapped field, API name, type, required flag, and for picklists the active value set. Compare to the last known good.A unit admin tightening a validation rule, changing a picklist, or altering field-level security on the integration user's profile. This broke INT-007 on 22 July.The integration fails from the target end with no source-side change, so every investigation starts by looking in the wrong place. In a Salesforce org this is the single most common cause of integration outage.NightlyLow.
4Create : update ratio canaryPer run, Contacts_Created / Contacts_Updated. Compare to the trailing 6-run average for the same integration. Alert above a per-integration variance threshold, default 100%.Matching logic silently failing. When a matching key stops resolving, the pipeline stops recognising existing constituents and starts creating them instead. INT-004 on 12 Aug: ratio 1.23 against a trailing average of 0.31, +297%. 214 Contacts created where roughly 55 were expected.THIS IS THE ONE THAT MATTERS. Every conventional check passes: the run completed, status is success, the error count is zero, row counts look normal. Nothing is rejected because nothing failed — the pipeline did exactly what it was told, against a broken key. The damage is 160 duplicate constituents that will be found months later by a gift officer, or never. There is no error to detect because no error occurred; the only signal is the shape of the output compared to its own history.Every runMedium. A legitimately new audience — a first-time event, an acquisition list — will trip it. That is the correct behaviour: those runs deserve a look. Suppress per-run with a reason, never per-integration.
5Stale integrationFor scheduled integrations: days since last successful run > cadence + grace. For the four bursty integrations: TODAY() > Expected_Next_Run__c, or the field is blank.An integration that stopped firing. INT-007 last succeeded on 22 July — 23 days of Registrar email engagement data missing.A stopped integration writes no rows and no errors. Absence of data generates nothing to alert on, so it is invisible by construction. It has to be derived from an expectation, which is why expected cadence is a required field and BR-3 exists.HourlyLow once BR-3 is in place. High without it — four of nine would show permanently red.
6Zero-row successRun status = success AND rows in file = 0.A broken filter, an expired token failing soft, or an empty source query. INT-009 on 1 July.Reports as green on every conventional chart and contributes a clean run to the reliability average, actively improving the score while doing nothing.Every runLow. Legitimate for genuinely quiet periods — suppress with a reason.
7Rows per unique personRows in file / unique persons in file, compared to the integration's own baseline.A join that fanned out in the source extract, or a legitimate multi-item event file. INT-004 on 12 Aug: 1.58 against a baseline of 1.12.Row counts alone look plausible. The inflation is only visible against the person count, which is why both are captured per run rather than just the row total.Every runMedium. Event and multi-gift files legitimately vary.
8Loaded with warningAt load time, evaluate the S1 rule set against each row that passed. Increment Records_Loaded_With_Warning__c and write a Data_Health_Defect__c with Introduced_By_Run__c populated.Rows that loaded successfully but carry a governance defect — no constituency, no preferred email, no GAU allocation, blank household greeting.With two buckets these count as clean successes. The log reports 99.6% while the backlog grows, and the two dashboards contradict each other. It also destroys attribution: a defect found in November cannot be traced to the May run that introduced it.Every runNone — it is a definitional bucket, not a heuristic.
9Human-account bulk writeRecords created or updated by a User who is not an integration user, above a threshold in a single hour, with no Integration_Run__c.Data Loader and import wizard sessions that bypass the middleware entirely. 10 Aug: 1,847 rows, 1,203 Contacts created, 235 rejected, no mapping, no owner.Completely invisible. There is no log, no run record, no mapping and no error report — the records simply appear. This check only exists because BR-1 gives every integration its own user, which makes a human write detectable by contrast.HourlyLow. Legitimate admin work will trip it occasionally and should.
10Multi-writer field conflictStatic analysis of Field_Mapping__c: count integrations writing each target field. Any count > 1 without a designated single writer is a conflict.Five pipelines writing the email opt-out field. The last one to run wins.Nothing detects this at runtime — every write succeeds. It is only visible from outside the system, when someone who unsubscribed receives another email, which is also the moment it becomes a compliance problem rather than a data one.On mapping changeNone — it is derived from configuration, not data.

Unit Score Model

The four score components, weights, formulas and known distortions, plus the warning about publishing letter grades.

ComponentWeightWhat it measuresFormulaNormalised byWhy this componentKnown distortion
Integration reliability30Are this unit's pipelines running, current, and attestedMean of: successful-run rate (7d), 100 if no stale integrations else 0 per integration, and attestation currency (100 current / 50 attested-but-modified / 0 never attested), averaged across the unit's integrations.Per integration, not per rowThe only component the unit fully controls without touching a single record. It rewards keeping mappings reviewed and noticing when something stops.A unit with one integration swings wildly on a single event. Report the component count alongside the score.
Record completeness30Share of the unit's attributed records free of S1 defects1 − (records with >=1 open S1 defect / records attributed to the unit). Attribution via Source_System__c and Created_By_Run__c.Per recordThe closest thing to a direct measure of data quality, and the one that maps to a worklist the unit can actually work.Legacy defects predating provenance are unattributable and sit outside every unit's denominator. Until BR-1 has a year of history this component measures recent work only — say so on the dashboard.
Defect introduction rate25New S1 defects created per 1,000 records touched, trailing 30 days1 − min(1, new S1 defects 30d / (records touched 30d / 1000) / ceiling). Ceiling set per unit type after baselining.Per 1,000 records touchedThe governance metric. It answers whether the problem is still being created, which backlog size cannot. A unit cleaning hard while its pipeline refills the bucket looks good on backlog and bad here — correctly.Bursty pipelines concentrate a year of defects into one afternoon. Registrar scores 22 on this from a single semiannual load. Volume normalisation helps but does not fix it — see the note below.
Remediation responsiveness15Are open S1 defects being worked1 − (open S1 defects aged > 30 days / total open S1 defects).Per defectSeparates units with a big inherited backlog they are working from units with a small backlog they are ignoring.Rewards closing easy defects first. Pair with a severity-weighted view before this drives anything consequential.
Bands
A90–100No open S1 alerts, all mappings attested within cycle
B75–89Healthy. Worklist is short and current.
C60–74Attention. One structural problem, usually attestation.
D45–59At risk. Typically an unattested pipeline that has misbehaved.
F0–44Intervene. Central team leads remediation, not the unit.
Read this before the score is shown to anyone senior.
A composite score exists to be clicked, not quoted. It compresses four unrelated things into one number, and the compression is where the argument will happen. Three rules: always render the four components beside the composite so the score can be interrogated in the same glance; never publish a cross-unit ranking before every unit has had a worklist and one quiet cycle to act on it; and accept that the two lowest-scoring units under this model — Registrar and Events — do not have a data entry problem. Both run bursty pipelines that introduced thousands of defects in a single afternoon. The score is measuring one bad run, correctly, but a leader reading only the letter grade will conclude something false about the people in those units. If the score cannot be shown with its components, do not show it.
