The 10 Aug row — how an unlogged load became visible
FLAG  created by a non-integration User  AND  no Integration_Run__c  AND  count > threshold/hour

1,847 rows, 1,203 Contacts created, 235 rejected. No mapping, no owner, no matching configuration, no run record. It is the largest Contact-create event of the week and it did not come from an integration.

This row exists only because of BR-1

Before dedicated integration users, a Data Loader session was completely indistinguishable from any other write. No log, no run record, no mapping, no error report — the records simply appeared, and the only trace was a CreatedById nobody was looking at. Giving every pipeline its own user makes a human bulk write detectable by contrast: records created by a person, at volume, with no run attached, are now a queryable set. Detection is not prevention. BR-2 is what stops it, and BR-2 is a policy change — routing manual files through an Omatic file-import profile makes the logging structural rather than dependent on anyone's discipline.

Why raw messages are normalised before they are counted

340 distinct error strings resolve to six problems. Without a pattern-to-category mapping table the panel shows hundreds of one-off rows and nobody can tell which is systemic. The unclassified rate is the maintenance signal for the mapping table itself — when it climbs, the categories have fallen behind the errors.
