The canary — create : update ratio against trailing average
PER RUN  Contacts_Created ÷ Contacts_Updated  vs  trailing 6-run mean  ·  alert > 100% variance

INT-004, 12 Aug: ratio 1.23 against a trailing average of 0.31 — a 297% deviation. 214 Contacts created where roughly 55 were expected. When a matching key stops resolving, the pipeline stops recognising existing constituents and starts creating them instead. Creates spike, updates collapse, and the ratio moves long before anyone notices the duplicates.

Why this is invisible to every other check — the single most important note on this page

Nothing failed. The run completed. Status is success. The error count is zero, and it is zero correctly — no row was rejected because no row was invalid. Row counts look normal. Volume is unremarkable. The pipeline did precisely what it was configured to do, against a broken key, and every conventional monitor reports green. A dashboard built on run status and error counts alone would have shown this run as one of the healthiest of the week.

The damage is roughly 160 duplicate constituents, found months later by a gift officer holding two records for the same donor, or never found at all. There is no error to detect, because no error occurred. The only available signal is the shape of the output compared against the integration's own history — which is why created and updated are stored as separate counters per run rather than rolled into a single "records processed" figure. Roll them up and this alarm becomes unbuildable.

Staleness — deriving an alert from the absence of data
SCHEDULED  days since last success > cadence + grace  ·  BURSTY  TODAY() > Expected_Next_Run__c  OR  blank

INT-007 last succeeded on 22 July. It failed 31 times on a field-level security error, then stopped. Twenty-three days of Registrar email engagement data are missing.

Why nothing alerted

A stopped integration writes no rows and no errors. Absence generates nothing to alert on — it is invisible by construction, and no amount of monitoring the log will surface it, because there is no log entry to monitor. It can only be derived from an expectation, which is why expected cadence is a required field. BR-3 is what makes this usable: four of nine integrations run in bursts, and cadence-based logic would show 44% of the register permanently red — which teaches people that red means nothing and destroys the panel. The expected-next-run date, set as the closing step of each run, is the only thing separating a genuine alarm from a wall of noise.

Three buckets — why "success rate" is not a column here
rejected + warned + clean + unchanged + skipped  =  rows in file  ·  no residual, every run

Rejected did not load. Loaded with warning loaded but carries a known S1 governance defect — no constituency, no preferred email, no GAU allocation, a blank household greeting. Loaded clean passed every rule. The warning bucket is populated by evaluating the S1 rule set at load time, not overnight, so the defect is written with Introduced_By_Run__c already populated.

What two buckets would hide

Collapse warned into clean and the Greater Giving run on 12 Aug reports 96.9% success — a good week. Forty-one records loaded carrying defects that will appear on board 06 as a worklist, and nothing connects them back to this run. The pipeline dashboards would report health improving while the defect backlog grew, and the two halves of the programme would contradict each other in front of the people being asked to fund it. The warning bucket is the join. It is also the only reason defect attribution works at all: a defect found in November can be traced to the May run that introduced it, because the link was written at load time rather than inferred later.
