What this is, and what it scales to

A mockup of an idea for how to construct data quality and integration health dashboards. It was prototyped against a proof of concept with five decentralised units creating and entering data:

Alumni RelationsDevelopmentEvents Marketing & CommunicationsRegistrar Office

Five units is small enough to name every integration on one page and interview every owner in a fortnight, which is why it is the right size to prove the model on. The same functionality scales without redesign to an institution with thirty units. Nothing here is hard-coded to five: the register, the run log, the exception log and the defect log are all keyed on unit and integration, so a thirty-unit deployment adds rows, not structure. Boards 01, 04 and 05 grow by filtering and sorting rather than by adding panels. Board 02 is the one that changes shape — thirty unit panels do not fit on a screen, so it becomes a ranked exception view showing only units with an open alarm. Board 06 is already one instance per unit and simply gets instantiated thirty times.

Two things get harder at thirty, and both are governance rather than engineering: the number of writers on any shared field grows, so the single-writer decision becomes mandatory rather than advisable; and the interview inventory that takes two weeks here takes a quarter, which argues for a self-service registration form rather than a spreadsheet.

Nine data integrations across five units and seven source systems. Two carry a primary and a secondary business owner — Gratavid and Greater Giving are single vendor accounts serving two units each, which is what takes the register from eleven rows to nine and Contact-create paths from four to three. Six boards, one data model: everything except the defect backlog is a different lens on the same run log, so a unit view, a seven-day log and a semiannual audit are filters rather than separate builds. The purple notes throughout explain how each alert is derived — the logic behind it, what it catches, and what would go undetected without it. Read those before challenging a number.

BR · D · F · —Open appendix
Build requirements — the full set behind these six boards, all proposed
BR-1 · proposed

Provenance on every record, day one

Source_System__c, Created_By_Run__c, Last_Integration_Update__c and a unique Source_Record_Id__c on Contact, Account and Opportunity, plus a dedicated integration user per pipeline. Cannot be applied retroactively — every week of delay is another week of unattributable records.

BR-2 · proposed

Mandatory intake for manual uploads

Manual files route through an Omatic file-import profile so logging is structural. Screen Flow is the exception path. Acceptance: zero Contacts created by a human account in a 30-day window with no run record.

BR-3 · proposed

Expected next run set at close of run

Enforced by validation rule on the four bursty integrations — Greater Giving, SIS, Gravyty, iWave. The run cannot be marked complete until the date is set. Close of run is the only moment anyone knows the answer.

BR-4 · proposed

Three buckets, not two

Rejected · loaded with warning · loaded clean, on every run and every board. The warning bucket is the join between the pipeline dashboards and the data health dashboard.

BR-5 · proposed

Student ID crosswalk on the graduate import

Store the SIS student ID on Contact as a unique External ID at first load, and configure Omatic to key on it before any name or date-of-birth fallback. Every subsequent cycle then becomes an upsert instead of a fresh fuzzy match. Currently zero of 3,959 loaded graduates carry one. Blocking for the December cycle — retrofitting after another name-and-DOB load costs more than building it now, and the duplicates it prevents are the expensive kind.

BR-6 · proposed

Attestation as a record, not a checkbox

Two independent dates on every integration — Mapping_Last_Modified__c from Omatic and Mapping_Last_Attested__c from a human — plus the version reviewed, the reviewer, the method used, and any accepted exceptions. A checkbox gets clicked reflexively; a form asking which version and which method does not.

BR-7 · proposed

Source and target schema fingerprinting

Capture the field list the source returns on every run and diff it against last known good. Do the same on the Salesforce side — API name, type, required flag, and active picklist values for every mapped field. Source drift catches a vendor adding a field; target drift catches a unit admin changing a validation rule or picklist, which is the more common outage in a Salesforce org.

BR-8 · proposed

Rolling canary baseline per integration

Store created and updated as separate counters on every run and maintain a trailing six-run mean of the create:update ratio per integration. Roll the two into a single "records processed" figure and the canary alarm becomes unbuildable — there is nothing left to compare.

BR-9 · proposed

Error category normalisation table

A maintained pattern-to-category map turning raw vendor and Salesforce error strings into a controlled set: validation rule, required field null, invalid picklist, duplicate rule, field-level security, lookup missing, matching ambiguity, API limit, unclassified. Track the unclassified rate — it is the maintenance signal for the table itself.

BR-10 · proposed

Acknowledged-exception suppression

Every defect rule needs a reviewed-and-accepted state carrying a reviewer, a reason and a re-review date. Without it the same few hundred unfixable records appear on every monthly report, staff learn the list contains known noise, and the board is dead within two quarters. Costs almost nothing now; close to unrecoverable once trust has gone.

BR-11 · proposed

Segmented pre-load gate on the graduate import

Block the load when any school, degree level or term segment varies from the registrar's own count by more than the tolerance — not when the file total does. Spring 2026's aggregate variance was −2.0%, comfortably inside any file-level threshold, while Education was 23.7% short. Also required: a tier-C hold queue with a named owner, since possible matches must neither auto-create nor auto-merge.

BR-12 · proposed

Dual-owner countersign on shared integrations

Gratavid and Greater Giving each serve two units from one vendor account. The primary owner holds the mapping; the secondary countersigns any change, and both see the integration on their unit board. Rows and defects attribute to the unit whose event or campaign produced them, not to the primary owner.
